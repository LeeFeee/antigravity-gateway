整理日期：2026-11-16。本文已只读核对开发目录的 `package.json`、入口及相关模块，开发版本为 Antigravity Gateway 2.0.5；本机安装和服务器运行版本未在本轮核验，正式执行前须分别复核。目标发布版本：尚未指定。

状态：需求基线。用户已明确启动改造；实施和实际验收进度见[协议取证与实施记录](gemini-app-protocol-evidence.md)。已确认约束、设计建议、待探测事实和待决定事项分别列出。本文件不是实现完成或真实验收通过声明。

**2026-11-16 范围修订（以用户最新指令为准）：Google Gemini API 只接入 Gemini app 的任务模式（Task），不接入聊天模式（Chat）。基于已经取得的真实任务接口构建；停止为 Chat 的 High/Medium 兼容继续探索替代工具线路。模型目录、普通文本、工具调用、搜索及 Auto 审批均以 Task 协议及其实际能力为准。登录、首次初始化、不参加改进计划、双池隔离和原 Antigravity 功能保留要求不变。历史 Chat 取证仅保留为研究记录，不算产品能力或后续验收目标。**

**同日执行顺序补充：五个客户端必须通过各自正常配置接入，再真实调用验收，全部通过后才允许发布。任务模式多模态暂不处理，后续另行确认。先保证整体可用，再处理耗时。首次初始化与隐私确认放在最后：目标是捕获 Gemini app 首次登录弹窗中“不参与改进计划”选择及确认用户条款的实际请求，并由网关自动完成相同步骤；不得以只关闭活动记录代替这项弹窗流程的完整证明。本阶段以该首次弹窗实际出现的条款和改进计划选项为核验对象，不扩展为全应用所有隐私开关的审计。此补充优先于下文早期探测次序与多模态验收条目。**

本文最初按“仅整理、不探测、不改代码”的要求形成；后续用户已明确要求按本文开始改造并自主执行。下文保留需求形成时的未知项，实际取得的证据在实施记录中更新；凡未取得对应证据的接口、字段、模型和初始化能力，均不视为已验证。

本文合并本轮双上游接入讨论及需要继续保留的既有网关约定，不将历史退役通道的能力当作新实现的已知事实。

## 1. 目标与约定

网关同时提供两个明确隔离的上游：

| 展示名称 | 协议来源 | 推理运行方式 | 账号来源 |
| --- | --- | --- | --- |
| Google Antigravity API | 已适配的 agy 请求协议 | 网关直接请求上游 | Antigravity 账号池 |
| Google Gemini API | 后续从本机 Gemini app 实际请求中确认的协议 | 网关直接请求上游 | Gemini 账号池 |

“Google Gemini API”是本项目对 Gemini app 对应上游通道的名称，不表示已完成其他 Gemini API 产品的接入。

硬性边界：

1. 本地、Linux 服务器上的正常推理均不依赖 Gemini app 安装、启动或在线。
2. Gemini app 是协议取证对象，不作为推理桥接、子进程推理或故障兜底。授权阶段允许用户完成必要的官方登录操作，具体方式待取证确认。
3. 客户端继续使用现有 Anthropic Messages / OpenAI Responses 入口、网关密钥与端口；通过模型名选择上游。
4. 账号只通过看板添加。新增“添加 Gemini 账号”，不增加凭据文件导入或自动导入本机登录态的产品入口。
5. 保留现有安装命令、路径、密码、API Key、端口、Antigravity 账号和历史数据。
6. 不自动启用旧 Robin、Windows Gemini 账号目录。旧文档与历史抓包只能作为线索，不能代替当前 Gemini app 的实际证据。
7. 首次添加 Gemini 账号时，目标是在看板授权流程内通过直接接口完成必要的首次初始化与协议确认，并明确选择“不参加改进计划”。是否存在可用的直接完成方式，需要实机取证和验证。
8. Claude Code Auto 审批跟随主请求所属上游：Antigravity 使用现有 Flash Low，Gemini 使用该上游经验证的相应审批模型。
9. 最终验收使用本机真实 agent 的完整请求与真实工具执行，覆盖本地网关和服务器网关；测试方法详见第 8、9 节。
10. 现有图片生成默认开启的约定继续保留，不要求用户重新打开配置。保留能力不表示把 Antigravity 的生图请求偷偷用于 Gemini 模型；新增 Gemini 生图能力须单独取证与验证。

保留现有默认模型与客户端接入方式。本轮未要求增加 Chat Completions 接口、改变默认上游、恢复退役通道或引入跨上游自动降级。

## 2. 模型命名与路由

现有 Antigravity 对外模型名保持兼容。新增 Gemini 模型统一以 `-g` 结尾，例如：

- `gemini-4-hydrogen-g`
- `gemini-4-argon-g`
- 只发布任务模式已验证的档位；当前任务目录及实际响应均为 Low，可提供 `gemini-4-hydrogen-low-g` 和 `gemini-4-argon-low-g`。不从 Chat 策略导入 High/Medium。

上述名称是产品示例，真实上游 ID、账号权限、档位及能力尚待探测，不能据此提前发布模型。

模型注册表须明确保存：公开 ID、显示名称、上游类型、真实上游 ID/枚举、思考配置、模型能力、所需账号权限及来源证据。审批辅助模型另登记用途与所属上游。路由不能依赖盲目删除 `-g` 或模糊匹配提示词。

- 注册且属于 Gemini 的公开模型，只进入 Gemini 账号池。
- 不存在的 Gemini 模型不能降级成 Antigravity 模型；没有对应可用账号时返回该池的真实错误。
- 模型别名解析后仍保留唯一、明确的上游归属，拒绝歧义配置。
- `/v1/models`、看板和客户端目录一致展示公开 ID，并标识来源及已确认能力。
- 临时冷却不等于模型不存在；目录状态与即时可路由状态分开处理。
- 对外响应保留公开模型 ID；日志另记录实际请求 ID、上游类型、上游模型 ID 和返回的模型版本标识（若提供）。
- 带档位模型名是强度的明确约定，冲突的客户端思考参数直接忽略，不报错、不警告，也不覆盖模型名对应的上游配置。没有证据的档位不发布。

同一模型家族若同时出现在两个上游，按来源保留两个公开条目，不因名字相似合并。账号没有权限、额度暂不可用、模型不再提供和目录查询失败须分别表达，不能统一转换成“模型不存在”。

## 3. 账号、额度与会话

使用两套独立账号池，复用现有会话粘性、可用性判断、权重和轮换策略。认证、额度获取、模型权限和错误识别由对应上游实现。

建议在原数据根目录新增 `gemini-accounts/`；现有 `accounts/` 原位沿用。Gemini 调度、额度、会话及必要协议状态使用独立存储命名空间。

必须同时隔离：

- 凭据及其刷新、重新授权代次、删除和异步更新。
- 账号 ID、额度缓存、健康状态、冷却和统计索引。
- 会话粘性、上游会话游标、工具结果关联、思考签名、文件上传引用和缓存引用。
- 不同网关调用者的会话与资源访问范围。

同一个 Google 邮箱可以分别加入两个池，但授权、额度与状态不能合并。目录隔离不能代替共享统计和状态索引的隔离；旧账号标识保持兼容，新 Gemini 标识必须有唯一归属。

调度规则：

1. 绑定账号仍有效、具备模型权限且可执行时，优先沿用。
2. 账号失效、额度不足、冷却或无模型权限时，在同一上游池内按现有规则选择其他可用账号。
3. 不等待原账号恢复后才能继续，不补造客户端历史，不增加跨账号任务恢复机制。
4. 上游必要的会话/工具关联仅用于正确转发；若切换后无法接受客户端提交的状态，返回真实错误，由 agent 处理。
5. 已交付部分正文、思考或工具调用后发生错误，不换账号拼接另一条生成结果。
6. Gemini 与 Antigravity 之间不进行隐式兜底切换。

额度采用“共享判断框架、独立事实来源”：不预设 Gemini 与 Antigravity 使用相同单位、窗口、保留比例或共享额度。未知额度显示未知，不视为零或无限。额度不足、短期限流、容量不足、认证失效和请求错误应按可验证证据区分。

### 3.1 首次账号初始化与“不参加改进计划”

用户报告：Gemini app 新账号登录后可能出现协议/首次使用确认弹窗；未完成时可能无法通过接口调用模型。旧项目文档也记录过条款相关错误，但它只能作为探测线索。必须核实当前版本的实际弹窗、服务端状态、请求字段和失败原因，不能预先认定所有初始化错误都是未同意条款。

产品目标：免费 Windows 用户及无桌面的服务器，在通过看板完成必要 Google 登录后，无需安装 Mac Gemini app，即可完成账号初始化并使用其实际有权调用的模型。

账号添加的目标流程：

1. 用户在看板点击“添加 Gemini 账号”，完成对应上游的 Google 授权。
2. 查询账号身份、资格、首次初始化/条款状态和当前可选改进计划设置；具体接口以实际取证为准。
3. 已初始化的账号复核现状；未初始化的账号执行已确认的必要初始化步骤。
4. 明确区分必要协议确认与可选改进/数据分享选项。当前新增账号流程选择“不参加改进计划”，不能接受上游默认勾选作为替代。
5. 通过可验证的服务端状态、实际读回或其他直接证据确认初始化完成及“不参加”的最终状态。仅发送一个 `false` 字段、弹窗消失或本地记录“已完成”都不够。
6. 获取实际模型目录、权限和额度，对账号有权调用的模型做真实验证；成功后才标记为可用于相应模型的推理账号。
7. 如授权完成但初始化、偏好确认或推理验证尚未完成，在看板展示具体阶段与原因，不伪装成完全可用；允许按真实状态重试或继续。

必要约束：

- 必须查清“协议确认”“首次账号注册/设备注册”“模型使用资格”“改进计划选择”是否为不同操作，不把其中一个成功当作全部成功。
- “不参加改进计划”需要与真实界面文案和后台字段对应。不可假定它等同于关闭全部历史记录、所有诊断或其他无关 Google 隐私功能；不顺带改变流程之外的偏好。
- 若首次引导分别提供对话/文件用于改进模型、截图或其他媒体用于改进模型、使用情况统计、崩溃报告等可选项目，应逐项记录真实选项、默认值、提交字段及生效范围，对本次引导中的可选改进/上传项目明确选择不参加。不能只关掉其中一项便宣称全部完成；必要条款仍按其实际内容单独处理。
- 如果上游把拒绝改进与某项产品功能绑定，需记录实际影响，不虚构独立开关。若涉及引导之外的账号全局设置或额外功能损失，应作为需要明确的产品取舍，不能在实现时无声扩大修改范围。
- 加入新 Gemini 池的已初始化账号也按“不参加”目标核验；若原先已参加，后续需验证对应计划的退出方式与生效范围，不能因跳过首次弹窗就忽略这一要求。
- 重复添加、重新授权、令牌刷新和网关重启后，不能重新变成参加改进计划，也不能每次推理都重复执行首次初始化。
- 初始化步骤应按实际协议支持幂等或安全恢复；用户取消、账号删除、重新授权后，旧任务不能继续修改新授权的状态。
- Google 登录中的账号选择、验证码或二次验证与首次协议初始化分开处理；未获得或未验证的身份/同意状态不能伪造。
- 免费账号完成初始化不等于自动获得所有付费模型权限；不自动开通付费服务，不通过切换另一上游掩盖权限不足。
- 上游没有额度或没有目标模型权限时，应显示“已初始化但该模型不可用/推理未验证”等准确状态，而不是要求用户反复重新登录。
- 若事实证明必要确认只能依赖 Mac app、且不存在满足需求的直接方式，应明确记录该阻碍；不能偷偷改成 app 桥接后宣称 Windows/Linux 独立接入完成。

### 3.2 测试账号与授权范围

用户表示 Chrome 已绑定约 10 个 Google 账号，并授权在项目启动后通过这些账号进行登录与首次初始化流程测试；选择“不参加改进计划”。这一授权不表示当前开始操作。

这批账号是否包含真实未初始化、免费、具备目标模型权限的样本尚未核验。后续应先识别样本条件，按需要选择，不默认对全部账号重复接受协议或修改设置。

协议取证用账号与正式账号池分开管理。浏览器中已登录不等于自动加入网关账号池，临时探测授权不默认保存为正式账号。新上游的正式账号仍由看板添加。

## 4. Claude Code Auto 审批必须跟随上游

已确认要求：

| 主请求所属上游 | 审批上游 | 审批模型 |
| --- | --- | --- |
| Google Antigravity API | Google Antigravity API | 现有 `gemini-3.8-flash-low` |
| Google Gemini API | Google Gemini API | 该上游经实测能完成审批合同的模型，后续确认 |

不把 Gemini 的审批默认发送给 Antigravity，也不要求用户设置 `CLAUDE_CODE_AUTO_MODE_MODEL`、修改权限模式或关闭 Auto。

依据既有结构记录，需要重点核对两处固定绑定：主入口的独立分类器模型映射，以及 `src/anthropic-safeguards.js` 的固定审核模型。执行阶段先复核实际代码，两条实际存在的路径均须覆盖，不能只改其中一处。

必须覆盖两种客户端行为：

1. **主请求携带服务器审核合同**：在请求入口确定主请求的上游，把不可变的路由上下文传给审批调用。审批模型从该上游注册表选择，工具 ID、审核规则与结果合同保持对应。
2. **独立发送分类器请求**：探测实际的会话、父请求和任务关联字段，使用可靠关联确定主请求上游。不能只凭 `claude-sonnet-5` 判断来源，也不能按同 IP、同 API Key、全局“最近模型”或相近提示词猜测。

并发会话、同会话模型切换与在途审批必须保持各自正确的归属。已开始的审批绑定触发它的请求，不随之后的模型切换改变上游。

独立分类器沿用同一会话最近主请求所属的上游。有会话记录时，Antigravity 使用 Flash Low，Gemini 使用 Hydrogen Low；没有会话记录时保留既有 Sonnet 5 → Flash Low 兼容路由，不因为新增 Gemini 账号池而增加拒绝请求的条件。不使用网关全局最近请求覆盖其他会话，不伪造审批结果，也不修改客户端审批设置。此前关于“缺少关联就拒绝”的设计没有对应的真实失败样本，已按用户要求删除，不作为后续开发或发布的前置条件。

审批与主生成使用各自必要的上游任务状态，应用同一上游池内的调度策略；审批成功不重绑定主对话的私有任务状态。失败、超时、截断、非法 JSON/XML、缺失或重复工具 ID 均不能当作成功审批。

“跟随上游”是必须达到的验收目标。Gemini 的具体审批模型、输出合同支持程度、两种客户端行为的关联证据，都是探测与实施事项，不能预先宣称已解决。

## 5. Gemini app 探测范围

先记录实际安装版本、构建、平台和二进制摘要。对观察到的请求分类为推理必要、支撑能力、客户端专用；客户端更新或遥测不因出现于抓包就成为网关转发功能。

| 范围 | 需要确认的内容 |
| --- | --- |
| 认证与账号生命周期 | 登录授权、令牌交换与刷新、作用域、账号/设备注册、首次初始化、订阅资格、重登与撤销、跨设备和无桌面服务器可用性 |
| 首次协议与偏好确认 | 弹窗的必要/可选项目、条款状态与版本（若提供）、确认接口、改进计划真实字段、未确认时的错误、确认后的状态读回、重复初始化与取消处理 |
| 传输与公共封装 | 实际域名和路径、HTTP 方法、HTTP/TLS 特征、UA、版本/构建声明、必要请求头、压缩、序列化、超时和取消 |
| 模型目录 | ID/枚举、显示名称、Hydrogen/Argon 实际映射、账号可见性、上下文/输出上限、动态目录更新和缓存 |
| 思考参数 | 档位、数值预算、默认值、冲突处理、返回思考与签名；逐项对照实际发包和响应，不按名称臆测 |
| 普通生成与流式生成 | 系统/用户/模型消息、历史、生成参数、流式事件、增量/累计数据、结束原因、用量、响应内错误、截断及空响应 |
| 工具调用 | 声明与 schema、名称/参数限制、工具选择、并行调用、工具 ID、签名、结果回传、失败结果、多轮循环和 MCP 表达 |
| 会话与上下文 | 创建与续接、必要游标、会话和账号绑定、并发、模型切换、压缩/摘要（若存在）、缓存与恢复约束 |
| 图片与文件 | 文件上传、引用/下载、有效期、权限、图片理解、生成及编辑；能力由实际模型和接口决定 |
| 视频与其他媒体 | 视频表示/上传、理解或摘要、大小/时长边界；其他实际暴露媒体类型一并登记，未验证能力不对外声明 |
| 搜索与服务工具 | 原生搜索、来源/引用格式及工具回包；网关不额外抓网页或执行客户端工具来补造能力 |
| 额度与订阅 | 额度端点、单位、窗口、重置、共享组、按模型/能力的权限和耗尽行为、字段缺失和过期快照 |
| 错误与恢复 | HTTP 和流内错误、429 的具体类型、401/403、容量/网络失败、重试指示、取消、部分输出后的失败 |
| 时延与并发 | 授权/刷新、首次初始化、目录/额度、等待调度、首响应、首思考、首正文及完成耗时，失败重试与账号轮换的耗时贡献、并发限制 |

每类证据记录真实请求字段、调用顺序、必要条件、成功/失败响应、适用版本和仍未知项。原始认证数据、完整提示与日志保存在仓库外受限目录；仓库只提交脱敏说明、摘要和验证工具。

“尽量完善”意味着对已观察到的接口有可追溯清单，对必需链路完成真实闭环，对未触发/未知分支明确标注；不能以合成响应补成“全接口通过”。

对每个业务接口至少整理：触发动作、前置账号状态、端点/方法、认证与必要头、请求及响应 schema、字段语义/可选性、调用顺序、流式结束条件、错误与重试规则、可复用范围和证据级别。业务接口之间的依赖必须明确，避免把只在已有初始化账号上成功的调用当作全新账号也能成功。

字段目录还应区分固定协议常量、客户端版本声明、账号相关值、会话相关值和每次请求生成的值，标明缺省行为与是否允许跨请求复用。UA、模型枚举、工具声明等采用当前版本真实证据，不把历史抓包整段照搬成新的请求模板。

证据级别区分：当前 app 实际发包、网关直接请求真实上游、真实 agent 经网关闭环、静态代码/二进制线索、历史版本线索。静态符号存在不证明当前流程会调用，历史成功也不证明当前版本可用。

## 6. 统一转换与能力边界

路径为：客户端 Messages / Responses → 统一内部消息、工具与媒体语义 → 按模型注册表选择上游及账号池 → 上游适配器 → 统一结果 → 客户端协议。

- 共用客户端请求解析、错误输出、消息语义和工具合同；将 agy 专属请求封装与工具/会话处理留在 Antigravity 适配器。
- Gemini 的原生请求封装、传输、会话关联、工具表示与媒体处理单独实现必要部分；不为每个 agent 复制一整条推理管线。
- 保留用户 SOUL、自定义规则、技能、记忆、工具定义和执行权限；框架身份清理须有可靠来源。
- 工具标准化先依据真实语义建立映射：可等价转换的名称、参数、schema 与结果按目标协议转换，并保留可逆的名称/调用 ID 关联。不能把含义不同的工具强行改成某个官方工具，也不能虚构官方不存在的参数。无法等价映射时，优先使用该上游实测支持的通用工具声明；仍无法表达时明确返回兼容错误并记录能力缺口。
- 支持不了的工具或输出合同明确报错，不静默删除声明、把工具任务降级为纯聊天，或伪造工具结果。
- Shell、文件、浏览器、MCP 等客户端工具由 agent 执行。原生模型服务能力按既有边界转发，不扩大成网关通用执行器。
- 图片生成、视频理解、搜索和结构化输出按“上游＋模型”登记能力；现有 Antigravity 能力继续保留。不能默认向不支持的 Gemini 模型注入生图工具。

身份处理只针对能确认由客户端框架自动注入的身份声明。例如，确认来自框架模板的“你是某某客户端的官方助手”可按既有规则处理；用户 SOUL 中“你叫香香”、用户讨论 Claude Code 的正文、工具描述中的产品名称都不能因关键词匹配而删除。保留来源与转换规则的脱敏证据，不对整个系统提示做全局替换。

### 8.2 路由、故障与时延验收

- 同一 Google 邮箱分别加入双池，新增、重新授权、停用、删除和刷新只作用于所属池。
- 有效粘性被保留；不可用账号被按既有规则避开；失败时的池内切换不改变公开模型和上游归属。
- Gemini 故障不会触发 Antigravity 隐式兜底；另一上游正常请求仍可独立执行。
- 真实发生的 HTTP/流内失败、截断、取消、重试和已输出后中断均保留证据；未触发的分支不靠 mock 补齐验收。
- 时延区分客户端启动、授权/初始化、转换、调度、等待上游、实际生成、审批与重试。SSE 心跳或控制事件不能计为模型首字。
- 对比时记录账号、完整上下文体量、模型/档位、缓存和实际重试次数；不通过删工具、换模型或缩短用户规则制造提速结果。延迟目标尚未数值化，先建立可复核基线。
- 针对此前“一句你好也需一分钟”的问题，报告必须列出公开模型名实际对应的上游模型、提交的思考字段/数值/缺省状态，以及耗时发生在调度、上游思考、正文生成还是审批。按各自上游比较原生 app、直接请求和 agent 经网关的链路；不同模型或不同上下文的结果不能用于直接断言网关变快或变慢。Antigravity 的既有映射在回归中核对，Gemini 的映射通过新取证确认。

## 10. 实施顺序与完成标准

1. 先用已确认的 Gemini Task 真实接口完成整体可用链路，将五个客户端通过正常配置接入并真实调用验收。首次登录弹窗的初始化条款及“不参加改进计划”请求放在最后核实，多模态暂缓；耗时优化在功能可用之后处理。
2. 在隔离开发环境实现模型注册、双池隔离、统一调度接入、Gemini 适配器、首次初始化及看板管理。
3. 完成 Auto 按上游继承，包括当前固定 Antigravity 审批模型的两条入口。
4. 配置并运行本机真实 agent，按矩阵完成客户端请求 → 网关 → 真实上游 → 工具执行与回传的闭环。
5. 完成无 app 依赖的本地/Linux 独立运行验证，以及原 Antigravity 功能与数据兼容验证。
6. 根据实际证据确定可发布模型/能力、遗留问题和发布版本，再进入后续部署工作。

完成标准是双上游直接访问、正确模型归属、对应账号池与额度、池内粘性/轮换、首次初始化及“不参加改进计划”、同上游 Auto 审批、真实 agent 可用和旧部署兼容全部具备证据。当前阶段不宣称这些能力已经实现。
